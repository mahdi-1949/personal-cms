# گیت‌هاب و استقرار

## مخزن توسعه

مخزن عمومی پروژه `mahdi-1949/personal-cms` است. گیت‌هاب محل اصلی نگهداری کد، ثبت نسخه‌ها، بررسی تغییرات و اجرای تست‌هاست. استقرار روی هاست واقعی پس از تکمیل نسخه اول انجام می‌شود. انتشار frontend روی Pages اختیاری است و در این مرحله راه‌اندازی نشده است.

هر قابلیت روی یک شاخه `feat/...` یا `fix/...` توسعه می‌یابد. PR شامل توضیح رفتار و نتیجه تست‌هاست. شاخه `main` مبنای نسخه‌های بررسی‌شده خواهد بود. CI با push و PR، نصب وابستگی قفل‌شده، audit، `npm run check` و `npm test` را روی Node.js 24 اجرا می‌کند. حفاظت شاخه و الزام بررسی خودکار را مالک مخزن می‌تواند در تنظیمات فعال کند؛ فعال‌بودن آن در این نسخه ادعا نشده است.

سرورهای مشتری از نسخه مشخص کد استفاده می‌کنند. داده‌های SQLite، رسانه، نشست‌ها و بکاپ‌ها روی ذخیره مستقل همان مشتری می‌مانند. ارتقای نسخه پس از آزمایش staging و بکاپ انجام می‌شود. اطلاعات ورود هاست و کلیدها در تنظیمات امن سرویس استقرار قرار می‌گیرند. اتصال انتشار خودکار به هاست هنوز ساخته نشده است.

## اجرای بک‌اند

یک سرور یا سرویس سازگار با Node.js 24 و دیسک پایدار لازم است. API و پنل روی دامنه‌ای مانند `cms.example.com` با HTTPS اجرا شوند. SQLite و بکاپ نباید روی دیسک موقت یک محیط serverless رها شوند. این کد سازگار با Cloudflare Worker نیست و بسته‌ی Sites برای آن ساخته نشده است.

متغیرها: `NODE_ENV=production`، `CMS_HOST`، `CMS_PORT`، `CMS_DB_PATH`، `CMS_ORIGIN=https://cms.example.com`، `CMS_PUBLIC_URL=https://example.com` و `CMS_SECURE_COOKIES=1`.

TLS در reverse proxy و تنظیم timeout/حداکثر اندازه درخواست لازم است. Origin باید دقیقاً دامنه پنل باشد. در نسخه 0.3 دستور بکاپ کامل و بازیابی داده آزمایشی فراهم است؛ سرویس را متوقف و طبق [راهنمای بکاپ](BACKUP.fa.md) عمل کنید. کپی زنده فایل SQLite بدون توجه به WAL قابل اتکا نیست. زمان‌بندی، انتقال خارج از سرور و بازیابی آزمایشی روی هاست واقعی هنوز تنظیم نشده‌اند. هر نصب یک سرور نویسنده دارد؛ قفل کنار دیتابیس از تداخل عملیات CLI جلوگیری می‌کند. مسیر رسانه مستقل از دیتابیس نیز با `CMS_MEDIA_DIR` قابل تنظیم است.

## استقرار frontend

دو مسیر وجود دارد: frontend سروری همراه backend، یا خروجی ثابت روی Pages/هاست استاتیک. مسیر دوم برای سایت‌های معرفی ساده مناسب است؛ بعد از هر انتشار محتوا باید export و انتشار اجرا شود. نشر خودکار از پنل در این نسخه وجود ندارد. فرم تماس به بک‌اند Node نیاز دارد و از export ثابت حذف می‌شود. انتقال 308 سرور در خروجی ثابت به HTML انتقال تبدیل می‌شود.

برای Pages، `CMS_PUBLIC_URL` باید URL واقعی شامل زیرمسیر مخزن یا دامنه اختصاصی باشد. خروجی `dist` را روی یک مخزن/branch انتشار جداگانه یا از طریق artifact مخصوص Pages منتشر کنید. داده‌ی واقعی CMS نباید در runner از فایل‌های مخزن تأمین شود؛ اتصال امن انتشار به backend در مرحله‌ی بعد طراحی خواهد شد.

## شرط عرضه

تست‌های API/خروجی از طریق `npm test` اجرا می‌شوند. استقرار زنده، تست کامل مرورگر، آزمایش بازیابی روی هاست واقعی و بررسی مستقل امنیت در این مرحله انجام نشده است. قبل از تحویل تجاری مرحله‌ی عرضه در نقشه راه باید تکمیل شود.

## تنظیم امنیت نسخه 0.4

پیش از ایجاد محیط MFA/ایمیل، [راهنمای امنیت](SECURITY.fa.md) را اجرا کنید. `CMS_SECURITY_KEY`، تنظیمات SMTP و IPهای دقیق پراکسی در secrets سرویس قرار بگیرند. کلید با هر deploy تعویض نمی‌شود. پس از بکاپ نسخه قبلی و توقف سرویس، تصاویر قدیمی را با `npm run normalize-media` ارتقا دهید. تست دریافت لینک reset و اعلان و بررسی سیاست MFA روی staging لازم است.
